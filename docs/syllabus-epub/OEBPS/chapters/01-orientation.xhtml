Session 1: Orientation and the ZAP Baseline

Goal for this session: get the lab running, click through the store like an ordinary customer, then point ZAP at it and read the first report. Do not try to exploit anything yet. Every later session assumes you have a spidered site tree and a baseline scan to compare against.

1.1 Walk the Store First

Open http://127.0.0.1:8080 and behave like a shopper. Browse the catalogue. Open a product. Search for "bolt". Register an account, log in, place nothing in a cart because the cart is a stub, and look at your order history. Log in again as admin / Widgetorium2024! and notice the extra "Admin" link in the header.

While you do this, keep a notebook. Write down every parameter you see: search.php?q=, product.php?id=, orders.php?id=, the login form fields, the review form, the upload form, the /admin/ paths. A scanner will find most of these. You want to have seen them yourself first, because the ones you notice by hand are usually the ones the scanner cannot reason about.

1.2 Proxy the Browser Through ZAP

Start ZAP, set your browser to use it as an HTTP proxy (or launch the browser ZAP bundles), and browse the store again with the proxy recording. This seeds ZAP's site tree with real traffic, including the authenticated pages, before the spider runs. Manual browsing through the proxy is not optional polish; the spider will not find the admin report or the API endpoint on its own.

1.3 Spider and Baseline Scan

Run the traditional spider from the site root, then the AJAX spider, then let the passive scanner drain. The lab ships an Automation Framework plan that does exactly this:

docs/zap/run-zap.sh          # spider + AJAX spider + passive + active scan
                             # report lands at docs/zap/out/report.html

The wrapper runs the official ZAP image on the lab's internal network and reaches the app as http://webapp. Read docs/zap/widgetorium-zap-plan.yaml before you run it so you know what it is doing.

1.4 Read the First Report

The passive scan alone should already be flagging the cheap findings: the missing Strict-Transport-Security header, the self-signed certificate, information disclosure in error responses, the X-Powered-By banner. The active scan, once it finishes, should raise SQL injection on the search parameter and reflected cross-site scripting.

Now the more useful exercise: make a list of what ZAP did not flag. Expect it to stay quiet on the second-order injection, the IDOR on order history, the exposed .git directory, the predictable session token, and everything on the FTP box. Hold onto that list. The next four sessions are largely about the gap between it and the full count of nineteen.

1.5 Confirm the Lab Is Contained

Before you point anything sharper than a browser at this, prove to yourself it cannot reach past your machine.

./status.sh                                   # runs the bind audit, exits non-zero on any 0.0.0.0
docker compose ps --format '{{.Name}}\t{{.Ports}}'   # every mapping must read 127.0.0.1:
nmap -Pn -p 8080,8443,21 <this-host-LAN-IP>    # from another box: all filtered or closed

start.sh already refuses to launch a configuration that would bind beyond loopback, and status.sh re-checks the running containers. Run the external nmap once anyway. Getting in the habit of proving your lab is contained, every time, is a professional reflex worth building early, and it is the same check you will run on a client engagement to prove your test traffic stayed in scope.

1.6 What You Should Notice

An unauthenticated scanner sees a specific slice of a web application: the parameters that reflect, the headers that are missing, the errors that leak. It does not see intent. It cannot tell that order 1002 belongs to someone else, that a product name will be concatenated into a query an hour from now, or that the session cookie is a timestamp with a user ID stapled to the end. Those are the findings you carry a brain for. The rest of this course alternates between the two: let the tool sweep, then go where the tool cannot follow.
