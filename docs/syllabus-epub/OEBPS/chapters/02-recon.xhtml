Session 2: Reconnaissance and the Corporate Domain

Goal for this session: stop treating the lab as one IP on 127.0.0.1 and start treating it as an estate. Widgetorium runs its own nameserver, authoritative for a fake corporate domain, and behind that domain are hosts a port scan of a single address will never show you. Five findings here, an open zone transfer, a set of virtual hosts hiding behind the Host header, a certificate that hands over the guest list, a developer sandbox full of things nobody cleaned up, and an export bucket left open. None of them need an exploit. They need you to look.

The lab nameserver is on 127.0.0.1 port 5300, TCP and UDP. Port 53 belongs to your own machine's resolver and 5353 is taken by mDNS on macOS, so the lab uses 5300 and you point every tool at it explicitly. It is authoritative for two zones: corp.widgetorium.lab, the internal estate, and widgetorium.lab, the public face.

2.1 Passive First, and Why It Comes Up Empty

On a real engagement the first hour is passive: certificate transparency logs, theHarvester, amass in passive mode, a WHOIS lookup, Google. Run them here anyway, against corp.widgetorium.lab, and watch every one of them return nothing.

theHarvester -d corp.widgetorium.lab -b all
amass enum -passive -d corp.widgetorium.lab
curl -s 'https://crt.sh/?q=%25.corp.widgetorium.lab&output=json'

That is not a broken lab. The domain does not exist on the public internet, so there are no transparency-log entries, no scraped subdomains, no cached pages. This is exactly what an internal assessment of a private domain looks like: passive recon produces a blank page, and the tester who only knows the passive playbook is stuck. The move is to pivot to active, ask the infrastructure directly, and that is the rest of this session.

2.2 Ask the Nameserver

Start with the ordinary queries, by hand, before any enumeration tool. Read the SOA, find the nameserver, look for the obvious record types.

dig @127.0.0.1 -p 5300 corp.widgetorium.lab SOA
dig @127.0.0.1 -p 5300 corp.widgetorium.lab NS
dig @127.0.0.1 -p 5300 corp.widgetorium.lab MX
dig @127.0.0.1 -p 5300 corp.widgetorium.lab TXT
dig @127.0.0.1 -p 5300 www.corp.widgetorium.lab A

The TXT records alone are worth reading: an SPF string that names a mail host by IP, a DMARC record with a reporting address, a note that this is the internal zone. Now try the query that should never work against a stranger:

dig axfr @127.0.0.1 -p 5300 corp.widgetorium.lab

The whole zone comes back in one response. Every A record, the CNAMEs, the mail exchanger, every TXT string, and a set of hosts on 10.10.0.0/16 you had no other way to know about. This is finding 20: the zone allows a transfer from any client. allow-transfer was never restricted.

Do the same against the other zone and watch it behave correctly:

dig axfr @127.0.0.1 -p 5300 widgetorium.lab      # ; Transfer failed.

widgetorium.lab refuses the transfer, the way every zone should. Put the two side by side in your notes. The fix for finding 20 is one line: restrict transfers to known secondary servers, or turn them off, and keep an internet-reachable nameserver from ever holding the internal zone in the first place.

The enumeration tools do the same thing with parsing on top:

dnsrecon -n 127.0.0.1 -p 5300 -d corp.widgetorium.lab -t axfr

2.3 Which Names Are Real

The transfer handed you a list. Not all of it matters. Sort the records into three piles:

  • Points at 127.0.0.1. Live in the lab: www, shop, admin, api, dev, staging, legacy, ftp. These are your targets.
  • Points into 10.10.0.0/16. vpn, jenkins, ci, backup, mail, intranet-old. They resolve, but nothing in the lab answers on them, and security.txt (2.6) puts that range out of scope. Stale DNS is normal on real estates. Recording it is part of the job; scanning it here is not.
  • The wildcard. *.corp.widgetorium.lab resolves to 127.0.0.1 as well, which means every name you can think of resolves. Subdomain brute forcing by DNS resolution is useless here. You will have to enumerate a different way, which is the next step.

2.4 Virtual Host Discovery

The webapp on 127.0.0.1:8080 answers to more than the storefront. admin.corp.widgetorium.lab, dev.corp.widgetorium.lab and staging.corp.widgetorium.lab are separate name-based virtual hosts with their own document roots. A request with no Host header, a bare IP, or an unrecognised Host falls through to the shop, so nothing you did in Session 1 revealed them, and a port scan never will. This is finding 21.

By hand, send the Host header yourself and compare:

for h in www admin dev staging nope; do
  printf '%-9s ' "$h"
  curl -s -o /dev/null -w '%{http_code} %{size_download}\n' \
    -H "Host: $h.corp.widgetorium.lab" http://127.0.0.1:8080/
done

www and nope return the storefront, the same byte count. admin, dev and staging return something smaller and different. That difference is the whole detection. Now let a tool sweep a wordlist the same way:

gobuster vhost -u http://127.0.0.1:8080 --append-domain \
  --domain corp.widgetorium.lab -w <subdomains.txt>

The AXFR from 2.2 and the certificate from 2.5 both give you candidate names without guessing at all. To browse the hosts, add them to /etc/hosts pointing at 127.0.0.1, or keep using curl -H "Host: ..." and --resolve. The fix is a default virtual host that serves nothing useful, and keeping internal applications on their own listener or network rather than multiplexed onto the public one by header alone.

2.5 What the Certificate Gives Away

Even if the zone transfer were locked, the TLS layer would still talk. The internal HTTPS vhosts present their own certificate, selected by the SNI name you send in the handshake. Ask for one by name and read what comes back:

echo | openssl s_client -connect 127.0.0.1:8443 \
  -servername admin.corp.widgetorium.lab 2>/dev/null \
  | openssl x509 -noout -subject -ext subjectAltName

The subjectAltName lists thirteen hostnames. Cross-check them against the zone you pulled in 2.2: four of them, git, jenkins, vault and registry under corp.widgetorium.lab, are not in DNS at all. The certificate is leaking the intended host inventory, names someone planned for and put in the SAN, whether or not they exist yet. This is finding 22. Send a name that matches nothing instead and you get the storefront's certificate, the Session 4 one, with no SAN:

echo | openssl s_client -connect 127.0.0.1:8443 \
  -servername widgetorium.local 2>/dev/null \
  | openssl x509 -noout -subject -ext subjectAltName      # No extensions

testssl.sh will record the SAN list in its output too; reading it as a target list is your job, not the tool's. The fix is to stop enumerating internal hosts in a shared certificate: per-host certs, or a wildcard that names nothing specific, and keep internal-only names on an internal CA.

2.6 Read What People Left Behind

The dev vhost has directory listing on and is full of the things that accumulate on a box nobody owns. This is finding 23. Walk it:

B='-H Host:dev.corp.widgetorium.lab'
curl -s $B http://127.0.0.1:8080/robots.txt              # points at /s3/ and /notes/
curl -s $B http://127.0.0.1:8080/.well-known/security.txt # in-scope hosts, out-of-scope range
curl -s $B http://127.0.0.1:8080/phpinfo.php | grep -i 'PHP Version'
curl -s $B http://127.0.0.1:8080/notes/dev-notes.txt

The notes are the prize: staff names and the first.last username scheme, the svc-ldap-ro service account, the CI host's real address, a line saying ftpuser/ftpuser still works, and a reminder that the API key is still literal on staging. The admin vhost carries a listable /backup/ with a users-*.sql.bak that holds the real users table and its unsalted MD5 hashes, so you have the password hashes before you have touched the SQL injection in Session 3. Staging serves config.php.bak, the pre-refactor config with the database password and the API key in plain PHP, and a build-info.json with a version and a git commit.

Then there is the export bucket, finding 24:

curl -s $B http://127.0.0.1:8080/s3/ | xmllint --format -
curl -s $B -O http://127.0.0.1:8080/s3/widgetorium-migration-plan.pdf
exiftool widgetorium-migration-plan.pdf
curl -s $B http://127.0.0.1:8080/s3/backups/db-widgetorium-2024-11-04.sql.gz | gunzip -c

/s3/ returns an S3-style ListBucketResult naming its objects. The migration-plan PDF reads normally, but exiftool pulls its metadata: an author name and email, a Creator string that names the author's workstation, and keywords listing an internal host and a ticket number. The staff CSV gives you a full name list for a credential attack. The gzipped dump under backups/ has users rows and the API key in a comment. The fix across all of this is dull and total: directory listing off, no phpinfo or .bak files or notes in a document root, no unauthenticated buckets, and strip document metadata before anything is published (exiftool -all=).

2.7 What You Should Notice

You did not exploit anything this session. You asked a nameserver a question it should not have answered, you sent a header, you read a certificate, and you opened files that were sitting in the open. And you came away with an admin hostname, an API endpoint, a staging box that shares production secrets, two sets of password hashes, a username scheme, and a live API key. Every later session is easier because of it.

Notice too what the scanners did here. ZAP, pointed at the dev vhost, would flag the directory listing and the phpinfo page. It would say nothing about the zone transfer, the hidden vhosts, or the certificate's guest list, because those are dig, gobuster and openssl, not a web crawler. Recon is where the manual-first habit pays off first: the tools that matter here are the ones you drive yourself.
